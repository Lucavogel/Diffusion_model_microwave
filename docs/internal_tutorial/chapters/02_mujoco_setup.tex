\section{Build a Useful MuJoCo Benchmark}
\label{chap:mujoco}

Simulation is most useful as an engineering instrument: it allows the task,
controller, observations, recording format, and policy runner to be tested
without risking hardware. It should be sufficiently representative to exercise
the interfaces, but it does not need to reproduce every physical detail before
the first experiment.

\subsection{Start from the experimental question}

Before editing XML, decide whether the simulator must validate reachability,
camera information, teleoperation, data recording, or a complete policy
rollout. Add contact detail, textures, and dynamics only when they represent a
task requirement or explain a measured mismatch.

\subsection{The MuJoCo concepts that matter in practice}

MuJoCo describes the fixed system in MJCF/XML and stores the evolving state in
\filepath{MjData} \citep{todorov2012mujoco}. Keep the following distinction in
mind:

\begin{description}
  \item[Model:] bodies, joints, masses, geometry, cameras, actuators, and limits.
  \item[Data:] joint state, control input, object pose, contact state, and time.
  \item[Forward computation:] recomputes kinematics after directly changing state.
  \item[Simulation step:] advances dynamics by one time step.
\end{description}

To randomize an object's pose at reset, modify the data and call forward
kinematics. To change its mass or collision shape, modify the model description
and reload it.

\begin{methodbox}[A robust scene-building order]
Add the robot and a flat workspace first. Then add one primitive object, one
camera, and one success region. Validate reachability and contacts before adding
meshes, clutter, or multiple objects. Primitive collision geometry is usually
more stable than a detailed visual mesh.
\end{methodbox}

\subsection{Example scene from the internship}

The project scene is
\filepath{dp_mujoco/models/universal_robots_ur10e/scene_microwave_camera.xml}.
It separates scene geometry, robot description, environment access, and reset
randomization. Keep the same separation in a new project, and ensure collection
and execution use the same reset distribution.

Open any new scene before involving teleoperation:

\begin{lstlisting}[language=bash]
conda activate microwave_dp
python -m mujoco.viewer \
  --mjcf=dp_mujoco/models/universal_robots_ur10e/scene_microwave_camera.xml
\end{lstlisting}

Verify limits, initial overlaps, collision geometry, camera placement, object
settling, and repeated resets. Rendering without an exception is only the first
check.

\subsection{Design observations before collecting data}

Camera choice should follow the task. A global view gives workspace context; a
wrist view gives detail near contact but can be occluded by the gripper. Render
exactly the images that the model will receive, including their crop and final
resolution.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.86\textwidth]{camera_view.png}
  \caption{Simulation example: wrist view on the left and global view on the right.}
  \label{fig:sim-camera-example}
\end{figure}

Ask three questions for every camera:

\begin{enumerate}
  \item Is the relevant object visible before the action decision is required?
  \item Can the robot or gripper hide it during a critical phase?
  \item Can approximately the same viewpoint be reproduced on the real setup?
\end{enumerate}

Changing a camera, crop, or resolution after data collection changes the policy
input distribution. Treat it as an interface change, not a cosmetic edit.

\subsection{Add variation progressively}

Randomization should represent the uncertainty that the policy is expected to
handle. Define position and orientation ranges explicitly and sample only
collision-free states. Test many resets before recording demonstrations.

Useful stages are:

\begin{enumerate}
  \item fixed object and target positions;
  \item one-dimensional position variation;
  \item two-dimensional position variation;
  \item limited orientation variation;
  \item appearance, lighting, geometry, or object variation.
\end{enumerate}

If the policy fails after a new stage, this ordering identifies which added
uncertainty requires more data or a different observation.

\subsection{Validate the full simulation loop}

\begin{warningbox}[Touch pre-flight before the complete loop]
\filepath{launch_all.sh} requires a working 3D Systems Touch input path. Before
starting it, connect the device to the computer, power it when required, and
confirm that the vendor Touch driver and OpenHaptics are installed. The launcher
sources the ROS~2 workspace and builds it when generated files are missing; the
first build still requires a valid \filepath{OPENHAPTICS_ROOT}.

For a first installation, follow \cref{app:openhaptics} and verify
\filepath{/touch/pose} and \filepath{/touch/buttons} with the standalone ROS~2
driver before launching the complete teleoperation loop. Stop that standalone
test before running \filepath{launch_all.sh}, which starts its own Touch node.
For later sessions, plug in the device before launch and perform the daily
terminal setup described in \filepath{README_ENV.md}.
\end{warningbox}

In this project, simulation teleoperation is launched with:

\begin{lstlisting}[language=bash]
cd "$HOME/Stage_Lirmm/Diffusion-model-isaacsim"
conda activate microwave_dp
./launch_all.sh
\end{lstlisting}

The launcher starts the MuJoCo program and the ROS~2 Touch node. Before a large
collection, record only three episodes and verify:

\begin{itemize}
  \item the robot follows all Cartesian directions correctly;
  \item reset variation stays inside the protocol;
  \item both policy images update and have the expected resolution;
  \item actions and measured robot state evolve continuously;
  \item episodes can be saved, cancelled, and replayed.
\end{itemize}

Then train a small or short test run and execute one checkpoint in simulation.
This smoke test finds interface errors more cheaply than a full training run.

\subsection{Common mistakes and useful improvements}

\begin{longtable}{@{}p{0.30\textwidth}p{0.64\textwidth}@{}}
  \toprule
  \textbf{Symptom} & \textbf{First investigation} \\
  \midrule
  \endhead
  Unstable object contact & Check units, initial overlap, collision primitives, mass, and solver settings before changing control gains. \\
  Black or irrelevant camera & Check camera name, transform, lighting, render update, crop, and final resized image. \\
  Jump at reset & Clear velocities, apply the complete home/reset function, and recompute forward kinematics. \\
  Collection and rollout differ & Compare randomization, camera order, quaternion convention, image shape, and action scaling. \\
  Simulation is too easy & Increase one measured uncertainty at a time rather than adding arbitrary noise everywhere. \\
  Simulation is too slow & Profile rendering, physics, and policy inference separately; they require different fixes. \\
  \bottomrule
\end{longtable}

\begin{checkpointbox}[Ready for demonstration collection]
The task can be completed repeatedly by teleoperation, every reset is valid,
the policy observations contain the required information, and a saved episode
can be replayed without shape or convention ambiguity.
\end{checkpointbox}
